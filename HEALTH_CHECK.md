## Findings — Iteration 1 (baseline)

### Severity legend: 🔴 High · 🟠 Medium · 🟡 Low/Info

### 🟠 M1 — XGBoost version mismatch (model vs runtime)
- `requirements.txt:13` pins `xgboost==2.1.1`, but `docs/xgb_model_regeneration.md` repeatedly mandates `xgboost==3.2.0` and says *"Verify requirements.txt contains exactly xgboost==3.2.0"*. CLAUDE.md also says pin 3.2.0.
- At load, XGBoost emits: *"If you are loading a serialized model … generated by an older version of XGBoost, please export the model by calling Booster.save_model … first"* — confirming the 4 `models/*.pkl` artifacts were serialized under a **different** XGBoost than the 2.1.1 runtime.
- Risk: silent prediction drift / future hard-break on load. Either re-pin runtime to match training version, or re-export models under 2.1.1. **Decide which is the source of truth.**
- Model meta lacks the `xgboost_version`/`sklearn_version` keys the docs example claims it logs (`meta` = target/model_type/exported_at_utc/task only). Doc drift.

### 🟡 L1 — Orphaned / dead "matchup card" feature
- `/api/matchup-card/<game_pk>` is **not registered** in the running app (confirmed against `url_map`). Its code lives only in `api_matchup_card_route.py`, which is a paste-in snippet (`app` is undefined at module scope) and is **never imported** by `app.py`.
- `matchup_card.html` is likewise **not served** anywhere (no `_read_html_or_fallback` load, no route).
- `matchup_card.html` references `/api/matchup-card`, so the feature is fully dead on both halves. CLAUDE.md still documents the route as live.
- Action: either wire it up (paste route into `app.py`, add page load) or delete the orphaned files + remove from CLAUDE.md.

### 🟡 L2 — Stale per-day data files
- `data/lineups_*.json` only exist for `2026-06-17` and `2026-06-18`; today is `2026-06-20`. Same for `umpires_*.json` (06-17, 06-18 only). These are tiny (65–520 bytes) — likely empty/stub captures. Confirm the daily capture job is actually producing lineups/umpires.

### 🟡 L3 — Environment dependency drift (info)
- Fresh `pip install -r requirements.txt` pulled **pandas 3.0.3** and **numpy 2.4.6** (requirements only floor-pin `>=2.0` / `>=1.24`). pandas 3.0 has breaking changes vs 2.x. Production behavior depends on whatever Fly.io's image resolves at build time — non-reproducible. Consider pinning pandas/numpy upper bounds. (App imported & served fine under these versions in this env.)
- System `packaging 24.0` (debian-installed) blocks clean `pip install`; needed `--ignore-installed packaging`. Not a prod issue (Docker uses clean slim image) but noted.
